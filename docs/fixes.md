# Исправления и текущие ограничения

## Исполнение и восстановление

- Позиция становится `closed` только после подтверждённого закрытия всего
  сохранённого количества обеих ног. Ошибка или частичное исполнение оставляют
  позицию в `closing`; следующий проход закрывает остаток.
- Остатки ног, ценовой P&L и checkpoint начисления funding сохраняются в SQLite.
  Закрытая нога повторно не отправляется. Изменения состояния и запись исполнения
  фиксируются одной транзакцией.
- При входе обеим биржам задаётся одинаковое количество базового актива.
  Несовпадение фактических количеств вызывает закрытие пары, а не неподтверждённую
  корректировку номиналов. Комиссии отката также входят в учёт.
- Таймаут не доказывает отказ биржи. Автоматическое повторение ордеров удалено.
  Неоднозначное исполнение сохраняется с `needs_reconciliation`; новые входы
  блокируются. Автоматическая сверка таких live-позиций ещё не реализована.
- Временные метки используют UTC с часовым поясом. Старые даты без смещения
  интерпретируются как UTC.

## Расчёты

Все funding-пороги (`MIN_FUNDING_SPREAD`, `EXIT_FUNDING_SPREAD`) теперь заданы **за
час**. Существующие значения в `.env` нужно пересмотреть: файл не меняется миграцией.

Оценка входа:

```text
hourly_spread = short_rate / short_interval_hours - long_rate / long_interval_hours
expected_return = hourly_spread × EXPECTED_HOLD_HOURS
                - 2 × (long_taker_fee + short_taker_fee)
                - 2 × (long_entry_slippage + short_entry_slippage)
```

Оценка будущего выхода использует текущее проскальзывание как приближение.
Вычисление проскальзывания проходит по уровням стакана; недостаточная глубина
отклоняет вход. Paper-исполнение также расходует доступные уровни стакана.

P&L позиции включает funding, реализованный и нереализованный ценовой результат
обеих ног и комиссии. Дневной отчёт содержит **денежные события за день**: funding,
реализованный ценовой результат и комиссии. Нереализованная переоценка в дневной
денежный отчёт не входит. Снимки не суммируются как доход. Отчёт в полночь относится
к завершившемуся дню.

## Paper-режим

`PAPER_BALANCE_USD` задаёт начальный капитал **каждой** биржи. Свободный баланс
учитывает журнал денежных событий, занятую маржу и переоценку оставшихся ног;
кошельки и ключи не требуются. Используйте отдельную новую SQLite-базу для нового
эксперимента, не удаляя старую историю.

Paper-funding — оценка за фактически прошедшее время, а не реальные платежи.
Во время отсутствия данных и остановки программы funding не восстанавливается
по последней известной ставке. Paper-модель не симулирует ликвидацию, очередь
заявок и изменения стакана между запросом и исполнением.

## Nado и live

Исправлены публичные запросы: `/symbols`, gateway `type=market_liquidity`,
распаковка `data`, числовой масштаб `1e18` и archive `funding_rates`.
Последний возвращает **24-часовую** ставку, а не 8-часовую:
[документация funding](https://docs.nado.xyz/developer-resources/api/archive-indexer/funding-rate).

Старые вымышленные execute/WS-пакеты и подпись EIP-191 удалены. Подтверждение
`place_order` содержит `digest` и не доказывает исполнение:
[документация ордеров](https://docs.nado.xyz/developer-resources/api/gateway/executes/place-order).

`BOT_MODE=live` останавливается **до подключения и отправки ордеров**. Это
защитное ограничение, а не завершённая live-интеграция. Для снятия блокировки нужны:

1. Документированные подписи EIP-712 и округление по ограничениям каждого рынка.
2. Подтверждение fills, проверка остатков и восстановление неоднозначных ордеров.
3. Реальные балансы, маржа и funding-платежи с дедупликацией событий.
4. Интеграционная проверка на тестовой сети, включая разрыв соединения после отправки.

## Миграция и проверка

SQLite получает дополнительные колонки без удаления таблиц. Старые записи не
содержали режима торговли и интерпретируются как paper; их старые результаты
не пересчитываются задним числом. Для сопоставимой статистики начните новый paper-запуск
с отдельным `SQLITE_PATH`.

Локальная проверка:

```bash
python -m pytest tests/ -q
python -m ruff check src tests
```

Регрессионные тесты используют SQLite и моки бирж; они не отправляют реальные
ордера и не заменяют проверку подключения к публичным API.
