# Carry v2 — вход, удержание и учёт результата

Изменения активируются при следующем запуске `python -m src.main`.
Работающий процесс не перечитывает Python-код. При остановке учитывайте существующий
`SHUTDOWN_MODE`: `close_positions` закрывает позиции и платит комиссии,
`save_state` сохраняет их. Не запускайте два экземпляра на одной базе.
Старые сделки не пересчитываются; новые получают `strategy_version=carry-v2`,
старые записи без версии читаются как `legacy`.

## Вход

- Сканер сохраняет нормализованные часовые ставки в SQLite в пятиминутных корзинах.
  История строится по обеим площадкам синхронно. Разрыв наблюдений обнуляет пригодную
  последовательность. После чистого запуска минимум час наблюдений; повторные
  сканирования сами по себе не заменяют прошедшее время. Корзины дают точность
  продолжительности около пяти минут.
- Для выбранного направления все ставки спреда в пригодной истории должны быть
  положительными. Используется текущий непрерывный положительный период после
  последнего нулевого/отрицательного спреда; старая смена знака не блокирует всю
  связку на сутки. После смены знака снова требуется минимум час устойчивости.
  Прогноз — минимум текущего спреда и нижнего квартиля последних двух часов
  этого периода (`FUNDING_FORECAST_WINDOW_HOURS=2`),
  умноженный на 0,75. Отсутствие данных не разрешает вход.
- Горизонт прогноза — минимум `EXPECTED_HOLD_HOURS` и `MAX_HOLD_HOURS`.
  Час истории подтверждает устойчивость направления, но не ограничивает будущий
  срок удержания одним часом. Сохранение ставки на весь горизонт — допущение
  прогноза, не обещание дохода; при ухудшении действуют проверки выхода.
- Перед входом повторно запрашиваются funding, комиссии, стаканы и цены. Spot
  допустим только в лонг, perp в шорт с положительным funding.
- Доход ограничивается выплатами, попадающими в горизонт прогноза, отдельно для
  каждой ноги. Нормализация ставки к восьми часам не означает выплату раз в восемь
  часов: у Lighter применяется реальное часовое расписание.
- Для одинакового количества базового актива считаются четыре VWAP: покупка и
  продажа на каждой площадке. Недостаток ликвидности на стороне закрытия блокирует
  вход. Считаются четыре комиссии. Проскальзывание уже включено в VWAP.
- Добавляется резерв на неблагоприятное схождение цен, если середина стакана
  лонга выше середины стакана шорта. Для дохода также проверяется денежный funding
  обеих ног с разными ценами, а не только разница процентных ставок.
- Требуется `прогноз funding >= 1,5 × издержки + MIN_NET_PNL_AFTER_FEES × notional`.
  В логе `risk.entry_economics` есть стоимость оборота, резерв, доход, срок
  окупаемости и горизонт. Это оценка, а не гарантия сохранения ставок.

## Выход

`close_pnl_estimate` — funding + уже реализованный результат + результат закрытия
оставшегося количества по стаканам − уплаченные комиссии − комиссии закрытия.
Это отдельная оценка: обычный mark-to-market `net_pnl` не выдаётся за деньги,
которые точно останутся после выхода. Оценка может измениться до исполнения.

Низкий funding после трёх проверок больше не означает безусловный выход:

- первый час обычный выход по низкому funding не производится;
- после него можно выйти, если PnL закрытия покрывает буфер 0,01% notional;
- при небольшом минусе и положительном funding можно продолжить удержание,
  если консервативный дополнительный доход способен покрыть дефицит за оставшееся
  время, но не более `MAX_RECOVERY_HOURS` (8 часов);
- если восстановление не окупается, закрываемся с причиной `carry_cannot_recover_costs`.

Отдельные аварийные условия: устойчиво отрицательный funding 15 минут,
потеря 1% notional по PnL закрытия, неблагоприятное изменение базиса 2%,
`MAX_HOLD_HOURS`, недоступные данные после grace-периода. Они могут закрыть сделку
в минус. Минимальное удержание их не отменяет. Разрыв данных сбрасывает
подтверждение непрерывного отрицательного funding.

Монитор сравнивает результат изменения цен с фактическими ценами входа.
Исходная разница цен между площадками сама по себе не считается новым убытком.
Проверка большой исходной разницы перед входом остаётся фильтром несовместимых рынков.

После закрытия действует прежний cooldown символа 30 минут. Дополнительно две
убыточные сделки одной направленной связки за 48 часов блокируют эту связку на
24 часа от последнего убытка; состояние берётся из базы и переживает перезапуск.

## Funding в paper

Это моделирование, а не подтверждённые выплаты реального аккаунта:

| Площадка | Источник начисления |
| --- | --- |
| Hyperliquid, Entropy | История применённых часовых ставок; наблюдаемая oracle price около выплаты |
| Lighter Robinhood | История применённых часовых ставок; наблюдаемая index price около выплаты |
| Extended | История применённых часовых ставок; наблюдаемая mark price около выплаты |
| Polymarket Perps | История ставок за период контракта; наблюдаемая цена около выплаты |
| Nado | Изменение накопленного funding-индекса для соответствующей стороны × количество |
| Hibachi | Явная оценка по ранее наблюдаемой ставке и времени `next_funding_ts` |
| Hyperliquid spot | Ноль |

До расчётного события почасовые площадки не получают выдуманную дробную выплату.
Ставка следующего периода не применяется ретроспективно к предыдущему. Курсоры
событий и индексы сохраняются атомарно вместе с начислениями. Повторный опрос
не повторяет выплату. Перед закрытием производится последняя попытка начисления.

Историческая ставка не содержит точную историческую цену выплаты. Используется
ближайшая наблюдавшаяся reference price (по умолчанию максимум 180 секунд от события).
При пропуске цены, длительном простое или задержке публикации требуется восстановление
данных; неизвестный доход не придумывается. Ошибка перед аварийным закрытием не
запрещает закрыть риск и помечается `accounting_incomplete` в состоянии сделки.
Hibachi остаётся приблизительной моделью: API оценки не доказывает итоговую ставку.
Старая открытая позиция без funding-state начинает новый учёт с первого наблюдения;
прошлый пропущенный период не доначисляется по текущей ставке.

Базовая taker-комиссия Hyperliquid исправлена на 0,045%, maker на 0,015%; при
указанном аккаунте используются `userCrossRate`/`userAddRate` из `userFees`.
Комиссии остальных площадок остаются их API-значениями или явными настройками;
скидки и индивидуальные тарифы требуют проверки для конкретного аккаунта.

Источники: [Hyperliquid userFees](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint),
[тарифы Hyperliquid](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/fees),
[Extended funding](https://docs.extended.exchange/extended-resources/trading/funding-payments),
[Extended API](https://api.docs.extended.exchange/),
[Lighter funding](https://docs.lighter.xyz/trading/funding),
[Nado indices](https://docs.nado.xyz/developer-resources/api/gateway/queries/all-products).

## Проверка результата

События сканера и причины отказов исполнителя записываются в `LOG_FILE`
(`logs/arb.log`) в JSON, независимо от формата консоли. Файл ротируется по 10 МБ,
сохраняются пять предыдущих файлов. Раньше настройка создавала только каталог,
поэтому причины старых отказов в файле отсутствуют.

Тесты проверяют экономические сценарии и учёт, но не подтверждают прибыльность.
Сравнивайте новые сделки отдельно от legacy. Учитывайте и открытые позиции,
закрывающие комиссии, долю funding в результате, просадку, причины выхода и
пометки неполного учёта. Старые логи без полных снимков стаканов не позволяют
достоверно воспроизвести альтернативную стратегию на тех же исполнениях.

Нужно накопить новую forward paper-выборку. Maker-исполнение не включено:
для него отдельно нужны очередь исполнения, частичные fills и защита второй ноги.
Параметры 0,75/1,5/1 час/15 минут — исходные консервативные настройки, не результат
оптимизации на будущих данных. Они могут уменьшить количество входов до нуля,
если на рынке нет преимущества после издержек.
